## 一、目标

一句话：**这是一个以 AI Agent 为工作方式的文档工作台。**
用户在工作空间里组织材料，让 AI 去读、去审、去改，**产出直接落在文档本身**（Word 批注），
人再在同一个软件里看、确认、修改。业务场景是**标书审查**。

**所有被引入的东西都是工具，不是目的。** Electron 壳、office 库、渲染器、甚至「Word 批注」这个能力本身，
存在的唯一理由是服务上面这件事。由此：

- 不需要跟任何外部项目保持兼容，不为别人的 CI / 结构 / 版本约束买单
- 不合适就改、就删、就换
- 一个改动是否正确，只看它是否推进这条链路

## 二、链路：M0–M6

| 编号 | 名字           | 一句话                                                                      | 出自你的原话                                                                                     |
| ---- | -------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| M0   | 独立完整       | 别人 clone 下来就能跑，不依赖某台机器                                       | 「它应该是一个独立且完整的项目」「脱离我的计算机就完全无法工作，这肯定不行」                     |
| M1   | 工作空间       | 组织材料的方法                                                              | 「我们首先有组织 workspace 的方法」                                                              |
| M2   | 能力接入       | 能嵌入新的技能或 MCP                                                        | 「我们能去嵌入新的技能或者 MCP」                                                                 |
| M3   | 文档能力       | 把文档的处理/编辑/审阅能力集成进来——office 接进来，**我们自己就具备看和改** | 「我们能把这些能力都集成进来」「我们本身把 office 连接进来，我们就有了去看的能力或者编辑的能力」 |
| M4   | AI 审阅 → 批注 | AI 审阅，产出写进 Word 文档的批注信息                                       | 「能审阅，审阅产生了这个 word 文档的批阅信息」                                                   |
| M5   | 批注可见       | 我们软件里看得到审阅信息；外部编辑器打开也看得到（两边兼容）                | 「哪怕我拿外部的编辑器打开，也能看到批注信息。我在这个软件上能看到审阅信息」                     |
| M6   | 人审改         | 人类可以审阅，然后修改这个文档                                              | 「然后人类可以去审阅，然后去修改这个文档」                                                       |

## 四、缺口排序

1. **M3 的「看」和「改」** —— 最大缺口。没有它，M6 无从谈起，而整个产品就是「AI 审阅 + 人确认修改」。
2. **M4 从没真实跑通过一次** —— 环节各自的确定性部分都验过，但从没用真实模型走完「读 → 审 → 写批注 → 打开看」。
   bailian / qwen3.7-plus 那套配置还没用上。没跑过就不算通。
3. **M1 只在文档里** —— 目标的第一个环节，只有设计没有实现。
4. **M2 一行没做**。
5. **M5 的外部互操作没真验**。

## 五、我做的是否对得上方向

### 对得上的

| 事                                                          | 为什么对得上                                                 |
| ----------------------------------------------------------- | ------------------------------------------------------------ |
| M0：让项目自足（源码入库，clone 即可编译）                  | 「独立完整」是前提；此前换台机器连编译都过不去               |
| M4：打通解析 → 模型审阅 → 写 Word 批注                      | 直击主链路，且批注这一环是产品的差异点                       |
| 把面板与文档视图放到真实 Electron 上验证                    | 桌面应用只在单测里绿没有意义；这一步还挖出面板从未真正渲染过 |
| M0：CI 基线转绿（format / lint / architecture / typecheck） | 没有回归网，后面每一步都在赌                                 |
| 删掉外部项目的发布身份检查                                  | 那是别人的身份，不是我们的约束                               |

### 走偏的（这几条我认）

1. **把外部代码当成「上游」来对待**：花力气对齐它的 CI、保留同步通道、担心兼容性。它只是我拿代码的地方，
   拷进来就是我们的。
2. **围绕「要不要升版本 / 能不能兼容」反复打转**，而不是直接挑最简方案。
   你指出来后我才发现：自己编那套渲染层，版本问题根本不存在。
3. **问了不该问的**：编辑器界面放哪。工作区里点文件就该显示。
4. **把 M3 拆成了好几个我自己发明的「环节」**，还起了含糊的名字（比如「软件自己能看文档」），
   导致连汇报都说不清。M3 就是 M3。

### 一句话结论

**方向对，但离目标还差一大截。** M4 这条主干的下半段做通了；
而 **M3 的「看」和「改」是核心，被我当成了六步里的一步来对待**——它决定这个产品成不成。
